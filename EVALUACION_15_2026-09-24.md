## Esquema efectivo

```text
Telegram → OpenClaw (agente cesa, modelo conversacional)
         → herramienta cesa_lookup → HTTP local /api/chat
         → filtro de datos privados y de fecha futura
         → SQLite: fichas verificadas / malla aportada / fragmentos FTS5
         → respuesta, estado de evidencia, fuente → Telegram

Solo ante ausencia de respuesta: búsqueda de página pública concreta
  Apify vía Composio: implementado pero desactivado y sin credenciales verificadas
  refresh-one: consulta HTTPS directa a una URL fija, solo para piloto controlado
```

SQLite almacena e indexa; no entrena un modelo. No existe aprendizaje automático de las conversaciones. El modelo de OpenClaw no reemplaza una fuente CESA. Nido personal no se consulta.

## Piloto web acotado

Se hizo una única actualización `refresh-one` de `https://www.cesa.edu.co/experiencia-cesa/centros-de-apoyo/`, con comprobación de `robots.txt`, límite de tamaño, validación de host y sin entrar a Nido. Resultado registrado por el comando: `updated` con esa URL y **5 fragmentos** almacenados. El primer intento en sandbox falló con `WinError 10013` (socket restringido); la misma operación autorizada fuera del sandbox funcionó. La página oficial también se revisó manualmente. **No** se ejecutó Apify/Composio en vivo.

## Riesgos y siguiente ampliación

La recuperación de fragmentos FTS5 todavía puede devolver coincidencias de palabras sin responder realmente la intención; el caso 11 se corrigió con una regla puntual de abstención. Para ampliar cobertura de forma general, se necesita una capa de selección de pasajes por pregunta con evaluación de relevancia, versión/fecha de fuente y comprobación de que cada afirmación está respaldada. Las preguntas reales de estudiantes, anonimizadas con consentimiento, servirían para construir un conjunto de evaluación mayor. No se debe entrenar ni habilitar acceso personal a Nido solo para cubrir esas lagunas.
